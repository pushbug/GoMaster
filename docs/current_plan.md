# Current Plan

## Goal

Improve GoMaster's responsiveness, resource usage, and maintainability without changing Go rules, KataGo evaluation semantics, or the current user workflow.

## Phase 1 — Analysis Request Lifecycle

### Scope

- Add independently managed `AbortController` instances for KataGo analysis and Gemini coaching requests.
- Abort the previous request before starting a newer request of the same type.
- Abort in-flight work when starting a new game, undoing moves, changing mode, changing player color, or unmounting the game screen.
- Keep sequence guards as a second protection against stale results.
- Treat aborts as expected control flow so they do not switch the engine to mock mode or clear valid advice.
- Ensure loading and thinking states are released only by the request that currently owns them.

### Primary files

- `lib/hooks/useGameAnalysis.ts`
- `lib/hooks/useGoGame.ts`
- `lib/hooks/useBotTurn.ts`

### Verification

- Rapidly play, undo, reset, and switch modes while analysis is running.
- Confirm stale KataGo and Gemini responses never replace the current position.
- Confirm loading indicators stop after cancellation.
- Confirm one current request remains active after rapid interactions.

## Phase 2 — KataGo Bridge Reliability

### Scope

- Replace timestamp-only query IDs with collision-safe IDs generated by the server.
- Add a bridge method that settles every pending query with a mock fallback when the KataGo process errors or exits.
- Clear every pending timeout when a query settles or the process terminates.
- Prevent a duplicate query ID from overwriting an existing entry.
- Add a bounded FIFO queue for KataGo work. Keep one active query by default because a local analysis engine is the shared bottleneck.
- Allow queued stale requests to be cancelled before they reach the subprocess.
- Centralize query completion so response, timeout, cancellation, write failure, and process exit follow the same cleanup path.
- Register process cleanup handlers once and remove them when the bridge is destroyed.

### Primary files

- `lib/engine/validator.ts`
- `lib/engine/katago-bridge.ts`
- `app/api/analyze/route.ts`

### Verification

- Generate multiple requests in the same millisecond and confirm IDs remain unique.
- Simulate subprocess error and exit with pending and queued queries.
- Confirm every request settles once and no timer or pending-map entry remains.
- Confirm queued cancellation prevents KataGo from analyzing an obsolete position.
- Confirm mock fallback remains available when the local engine is unavailable.

## Phase 3 — Lightweight Replay Storage

### Scope

- Introduce a lightweight replay snapshot containing only the data required to render and resume a position.
- Keep move history in one canonical array rather than embedding the growing history in every snapshot.
- Avoid copying the full `boardHashes` set into every replay snapshot.
- Preserve exact undo behavior for normal moves, captures, pass, resign, handicap, Ko, and game-over states.
- Keep SGF export and match history based on the canonical live game state.
- Provide compatibility helpers so existing games and stored match records remain readable.

### Primary files

- `lib/go/types.ts`
- `lib/go/replay.ts`
- `lib/hooks/useGoGame.ts`
- `lib/go/rules.ts`

### Verification

- Compare every reconstructed position against the current snapshot behavior across 9×9, 13×13, and 19×19 games.
- Verify captures, Ko, pass, resign, handicap, undo, and replay navigation.
- Measure retained memory after a long 19×19 game and confirm snapshot storage grows linearly with move count.

## Phase 4 — Canvas Rendering Efficiency

### Scope

- Measure canvas redraw frequency during hover, variation preview, ownership display, resize, and normal play.
- Skip hover state updates when the board intersection and validity have not changed.
- Schedule pointer-driven redraws through `requestAnimationFrame`.
- Memoize variation-step construction for unchanged inputs.
- Remove redundant drawing-effect dependencies while preserving all visual updates.
- Split static and dynamic canvas layers only if profiling shows full-board redraw remains a visible cost.

### Primary files

- `components/go/GoBoard.tsx`
- `lib/go/board-renderer.ts`

### Verification

- Confirm coordinate mapping and clicks remain correct at all board sizes and device pixel ratios.
- Confirm hover stones, ownership, dead stones, and PV previews update without lag or stale frames.
- Compare frame time and redraw count before and after the change.

## Phase 5 — Maintainability Refactor

### Scope

- Extract `AppHeader`, `GameWorkspace`, and `AnalysisPanel` from `app/page.tsx` with explicit typed props.
- Keep game rules and side effects in hooks rather than moving them into presentation components.
- Replace broad setter exposure from `useGoGame` with named actions where practical.
- Evaluate a reducer for game transitions only after Phases 1–4 stabilize the current behavior.
- Keep components focused and avoid abstractions that merely move JSX without clarifying ownership.

### Primary files

- `app/page.tsx`
- `components/go/*`
- `lib/hooks/useGoGame.ts`

### Verification

- Confirm the desktop and mobile layouts remain visually equivalent.
- Confirm new game, play, bot turn, undo, replay, analysis, coaching, game over, and history flows remain functional.
- Confirm no client secret or server-only engine code crosses into the browser bundle.
